# 1. What you actually built

Your project isn't merely an MCP proxy.

The architecture you're aiming for is:

```text
                    AI Client
              Claude / Cursor / Agent
                       |
                       | MCP
                       v
              +-------------------+
              |   MCP Gateway     |
              |-------------------|
              | Authentication    |
              | Authorization     |
              | Policy            |

                        |
          +-------------+-------------+
          |             |             |
          v             v             v
       MCP Server    MCP Server    MCP Server
       filesystem    database      Jira/etc.
```

That is a **real infrastructure problem**.

Your README explicitly positions the gateway around aggregation/routing, policy, observability and rate limiting, with a single MCP endpoint for clients. ([GitHub][2])

And your Maven artifact means you're not asking people to clone a random repository and run a demo. You're attempting to make it a **Spring Boot starter**:

```xml
<dependency>
    <groupId>io.github.ashishgituser</groupId>
    <artifactId>mcp-gateway-spring-boot-starter</artifactId>
    <version>0.1.1</version>
</dependency>
```

That is a very important design choice. ([GitHub][2])

# 10. The rate limiter needs to evolve

Your current Bucket4j implementation is good for an MVP, but it's explicitly in-memory. You acknowledge that users can provide a distributed implementation such as Redis. ([GitHub][2])

For enterprise Kubernetes:

```text
Gateway Pod 1
Gateway Pod 2
Gateway Pod 3
Gateway Pod 4
```

an in-memory limiter isn't enough.

You should make the architecture:

```text
RateLimiter SPI
       |
       +-- InMemoryRateLimiter
       |
       +-- RedisRateLimiter
       |
       +-- future implementations
```

And ideally provide an official Redis implementation.

That gives you:

**stateless horizontally scalable gateway.**

# 11. You need better MCP transport coverage

This is extremely important.

MCP has evolved quickly, and Spring AI's MCP support has expanded around Streamable HTTP, SSE and different client/server transports. Spring AI's current MCP support explicitly includes Streamable HTTP and SSE among its transport options. ([Home][4])

Your project currently emphasizes Streamable HTTP in its E2E test. ([GitHub][2])

I'd make the compatibility matrix extremely visible:

| Transport       | Gateway | Upstream | Status            |
| --------------- | ------- | -------- | ----------------- |
| Streamable HTTP | ✅       | ✅        | Stable            |
| SSE             | ?       | ?        | Planned/Supported |
| STDIO           | ?       | ?        | Planned           |
| WebSocket       | ?       | ?        | —                 |

Don't leave users guessing.
